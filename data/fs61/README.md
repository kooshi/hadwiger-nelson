# `data/fs61/` — the census of real quadratic fields: what is here, who made it, and how far to trust it

*FS-61, `plans/FS61-quadratic-census.md`. Written at the close (phase F item F.1). Machine for every timing:
the desktop, 16 physical cores / 32 threads, 128 GB.*

## What the census is, in plain words

Colour every point of the plane whose two coordinates lie in the number field `ℚ(√d)`, so that no two points
exactly 1 apart get the same colour. The fewest colours that suffice is written `χ(ℚ(√d)²)`. Before this project
nobody had shown that **any** real quadratic field needs more than three. FS-58 showed six fields need four;
FS-61 runs one uniform procedure over the **whole family that can need four** — the forty square-free
`d ≡ 11 (mod 12)` below 500 — records where it lands and where it does not, and scores the guesses about what
decides that.

Everything here is either **a certificate** (a finite graph plus a machine-checkable proof that it has no
3-colouring), **a record** (one JSON line per unit of work, written as the work finished), or **a derived table**
(regenerated from the records by one command and never hand-edited).

## The one thing to read first

`census.md` — the census table, one row per field, regenerated by `python3 tools/fs61_census.py table`. Its header
explains every column, including the three different kinds of "not landed", which are three different kinds of
knowledge and must never be merged.

## Trust levels, and what each one means

Every row of the inventory below carries one of these. They are ordered, strongest first.

| level | what it means | what could still be wrong |
|---|---|---|
| **checker** | an independent program — standard library only, importing nothing from `tools/` — re-derived every edge in exact integer arithmetic from the coordinates and replayed the refutation proof line by line, and printed `CERTIFIED` | the checker itself. It ships twelve planted faults that must each be refused *for its named reason*, and every witness here was run against them |
| **exact** | computed in exact integer or rational arithmetic, with no solver and no floating point in the verdict | the program that computed it |
| **verified model** | a solver proposed an answer and an independent pass checked it against the full exact edge set — every "3-colourable" verdict here is of this kind, never a solver's bare word | the edge enumeration (see the asymmetry note below) |
| **solver claim** | a SAT solver said "no 3-colouring exists" and nothing has re-checked it | everything a solver can get wrong. **No claim of this milestone rests on one** — every refusal reported as a landing was carried to `checker` |
| **float reading** | a floating-point quantity used to aim work, never to decide a verdict — predicted ball sizes, predicted average degrees, character means | rounding; these steer the search and appear in no claim |

**The asymmetry that governs how to read a null.** Edges here are *measured*: a fast floating-point pass proposes a
pair and exact arithmetic decides it. So the only mistake possible is a **missed** edge, which makes a graph
*easier* to colour. A refusal is therefore robust, and a "3-colourable" verdict is the suspect one — which is why
every such verdict re-checks its colouring against the full exact edge set.

## The certificates — the only files a reviewer needs

`witness-<d>/witness.json` and `witness-<d>/witness.lrat.gz`, one directory per landed field. Each directory's own
`README.md` states the claim, the single command that re-checks it, and **what is not claimed** (every upper bound
here is prior art and is named). One command per field:

```
source scripts/dev-env.sh                                            # once per shell
python3 tools/fs58_check_witness.py --radicand <d> data/fs61/witness-<d>/witness.json
```

`CERTIFIED` and exit 0, or `REFUSED <CODE>` and exit 1. The exit status is read from the command, never through a
pipe.

| file in `witness-<d>/` | produced by | trust |
|---|---|---|
| `witness.json`, `witness.lrat.gz` | `python3 tools/fs61_census.py land <d>` → FS-58's frozen generator | **checker** (the two files *are* the certificate) |
| `certified.out` | `tools/fs58_check_witness.py --radicand <d> witness.json` | checker — verbatim output of gate item C.1 |
| `controls.out` | the same, `--controls` | checker — C.2; thirteen rows, the faithful twin certified and twelve planted faults each refused for its named reason |
| `wrong-radicand.out` | the same, `--radicand <d+12>` | checker — C.3; the witness is about *this* field and no other |
| `recheck.out` | `tools/fs58_recheck_witness.py <d> witness.json` | checker — C.4a, a second opinion in exact `Fraction` arithmetic with three solvers outside the generator's. **Read it as a transcript, not a verdict**: its last step is a separate *minimality* question (C.4b), and a witness can be certified with that step red |
| `colouring4.json` | `land` step C.5 | verified model — an explicit proper 4-colouring checked on every edge, so the graph is exactly 4-chromatic |
| `README.md`, `run-all.sh` | `land`, or `land-readme` to rewrite without a solver | prose and regeneration script |
| `generate.out` | FS-58's generator | provenance — the generator's own log, including every stop and its verification line |
| `steps.jsonl` | FS-58's `extract` | **gitignored**: megabytes of lattice coordinates. Provenance, not evidence — but it is what lets `run-all.sh` reproduce a stopped-deletion witness byte-identically, and each such `run-all.sh` says so in its header |

## The derived tables — regenerate them, never edit them

Each is written by one command from the records alone, so it cannot drift from what was measured. Regenerating one
without a record moving cannot change a verdict; that is the point of deriving them.

| file | command | what it is |
|---|---|---|
| `census.md` | `python3 tools/fs61_census.py table` | the census: one row per field, with its lattice states, how many balls were actually asked, the refusal bracket, the verdict and the evidence behind it |
| `controls.md` | `python3 tools/fs61_census.py regress controls` | the negative controls — seven fields whose planes are 2- or 3-colourable by theorem, scanned with the 3-integrality filter off, beside the same code path at `d = 47`, which must refuse |
| `dead-quotients.md` | `python3 tools/fs61_census.py dead-quotients` | which quotients kill a lattice, tallied by `d mod 8` and by 3-integrality |
| `readings.md` | `python3 tools/fs61_readings.py readings` | the readings scored — **won**, **lost**, **not decided** — each with the population it was counted over |
| `shapes.md` | `python3 tools/fs61_readings.py shapes` | the class-theorem attempt: which lattice *shapes* recur across fields, and the isomorphism table of the certified witnesses |
| `aiming-167.md` | `python3 tools/fs61_readings.py aiming167` | the note for FS-59: what this census says about `ℚ(√167)`, where the project's local–global conjecture predicts six or more and nothing above three is proved |
| `CLOSE-proposals.md` | hand-written | the implementer's proposals to the product owner at the close. **Proposals, not edits**: `CLAUDE.md`, `plans/FRONTIER-STUBS.md` and the stubs are his files |

## The phase records — `records/`

One file per phase (`phase-0.md`, `phase-A.md`, `phase-B.md`, `phase-Bprime.md`, `phase-C.md`, `phase-E.md`,
`phase-F.md`), each a table of *gate item · the pasteable command · the artifact · the line of output that shows
the pass · exit status*, plus the machine, the cost, the resume command written **before** launch, every planted
fault and the line it turned red, and anything that did not land, in those words. The product owner scores a phase
by re-running these commands; a claim with no row behind it is not read as evidence.

Also here: the raw logs (`land-*.log`, `selftest.out`, `table-check.out`, `phase-c-checks.out`,
`recheck-all.out`), and the `*.pid` / `*.pgid` files a long run writes at launch so it can be stopped by process
id rather than by matching a command line. Both patterns are **gitignored** as of the close — *a stale process id
is a trap, not a record*, and this repository has nine recorded incidents of a process being stopped by a
command-line match. Five `.pid` files committed by earlier phases (`deepen-2l`, `deg-1c`, `deg-2l`, `mem-455`,
`reask-1c`) are still tracked and are stale; they are provenance of those launches and nothing reads them.

`owner/` holds the product owner's own decorrelated recheck of the certificates (gate item C.10), run with his
code and two further solvers, with a sha256 per witness.

`pricing/` holds the opening day's measurements, made from a scratch copy of FS-58's tools so that `data/fs58/`
was never touched. It is **provenance for the plan's §2, not a result of the milestone**: its `witness-119/` was
priced and never certified, and the certified `d = 119` witness is `witness-119/` at the top level.

## Reproducing any of it

```
source scripts/dev-env.sh                          # required in any shell that runs the frozen checker

python3 tools/fs61_census.py selftest              # the instrument's own checks, each with a planted fault
python3 tools/fs61_census.py table --check         # re-derives the table and checks the accounting; changes no file
python3 tools/fs61_census.py status                # where every field stands, from the records alone
python3 tools/fs61_readings.py selftest            # every scorer shown able to return each of its verdicts
```

Every long-running command in this milestone **resumes by being re-run**; there is no separate resume flag.
Finished units are read back from the record file and skipped.

## What is frozen, and why

`tools/fs58_*.py` and everything under `data/fs58/` do not change. FS-61 *imports and calls* them. FS-58's
certified results rest on that code as it is, and the regression in phase 0 — which reproduces FS-58's lattices,
its five refusing balls and its five certificates — is meaningful only if the code under it has not moved.
`git status --porcelain data/fs58 'tools/fs58_*'` is empty at the end of every phase and is a gate item.

## What none of this is

**Nothing here is checked by the Lean kernel.** The certificates are an independent standard-library checker's,
which is a different and weaker thing. The one kernel result about a field in this table is FS-58's
`four_le_chromaticNumber_planeOver_eleven` (`Proofs/HadwigerNelson/Instances/SqrtEleven.lean`), a fact about
`ℚ(√11)` proved from a *different* 204-point graph; it is not a fact about any witness here. Kernel forms of these
witnesses are FS-60 (`plans/STUB-quadratic-witnesses-kernel.md`), and the witness format above is what FS-61 owes
it.

**And every upper bound is prior art**, named field by field in each witness `README.md` and in `frame.jsonl`:
the dyadic prime for `d ≡ 3 (mod 8)` (`[Fischer1990]` Thm 9), the residue plane at 7 or at 11 otherwise
(`[Moorhouse2010]` Thm 8.1). This milestone proves lower bounds only.
